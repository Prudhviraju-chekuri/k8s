Great — the Init Container + Sidecar pattern is a very common real-world Kubernetes design. Many systems like service meshes, logging systems, CI/CD pipelines, and data pipelines use this pattern.

I'll explain it clearly.

1️⃣ First Understand the Three Container Types in a Pod

A Pod can contain three kinds of containers.

Init Containers   → run first (setup phase)
Main Containers   → application containers
Sidecar Containers → helper containers running alongside main container

Execution model:

initContainers
      ↓
main containers + sidecars (run together)
2️⃣ Visual Flow
Pod Start
   │
   ▼
Init Container 1
   │
Init Container 2
   │
   ▼
Main App Container
   │
Sidecar Container

Init containers stop after completing.

Sidecars run for the entire life of the pod.

3️⃣ What is a Sidecar Container

A sidecar container is a helper container that runs alongside the main container to provide additional functionality.

Examples:

Main Container	Sidecar Container
web app	log collector
application	monitoring agent
API server	proxy
service	service mesh proxy

Both share:

network
volumes
localhost

apiVersion: v1
kind: Pod
metadata:
  name: login-app-pod
spec:

  volumes:
  - name: shared-data
    emptyDir: {}

  initContainers:
  - name: init-html
    image: busybox
    command:
      - sh
      - -c
      - echo "Login App Ready" > /data/index.html
    volumeMounts:
    - name: shared-data
      mountPath: /data

  containers:

  - name: login-app
    image: nginx
    volumeMounts:
    - name: shared-data
      mountPath: /usr/share/nginx/html

  - name: log-sidecar
    image: busybox
    command:
      - sh
      - -c
      - while true; do
          echo "Sidecar running";
          sleep 10;
        done

I'll give you a realistic but simple sidecar pattern that engineers actually use:

👉 Application container writes logs → Sidecar container reads logs and streams them

This demonstrates a log shipping sidecar, which is one of the most common real-world Kubernetes patterns.

Architecture
Application Container
       │
writes logs to file
       │
       ▼
Shared Volume (emptyDir)
       │
       ▼
Sidecar Container
       │
tails the log file
       │
prints to stdout

Both containers share the same volume.

Pod YAML (Login App + Log Sidecar)
apiVersion: v1
kind: Pod
metadata:
  name: login-app-sidecar
  labels:
    app: login-app
spec:

  volumes:
    - name: shared-logs
      emptyDir: {}

  containers:

  - name: login-app
    image: nginx
    volumeMounts:
      - name: shared-logs
        mountPath: /var/log/app
    command: ["/bin/sh"]
    args:
      - -c
      - |
        while true; do
          echo "$(date) login-app running" >> /var/log/app/app.log
          sleep 5
        done

  - name: log-sidecar
    image: busybox
    volumeMounts:
      - name: shared-logs
        mountPath: /var/log/app
    command: ["/bin/sh"]
    args:
      - -c
      - |
        tail -n+1 -f /var/log/app/app.log
What Happens Step-by-Step
1️⃣ Pod is created
kubectl apply -f pod.yaml

Kubernetes schedules the pod.

2️⃣ Kubelet starts containers

Both containers start in parallel.

login-app
log-sidecar
3️⃣ Shared Volume Created

Kubelet creates:

emptyDir volume

on the node.

Example path on node:

/var/lib/kubelet/pods/<pod-id>/volumes/
4️⃣ Volume Mounted

Both containers mount it.

login-app  → /var/log/app
sidecar    → /var/log/app

So they share:

/var/log/app/app.log
5️⃣ Application Container Writes Logs

Inside login-app:

while true
  echo "login-app running"

Every 5 seconds it writes:

/var/log/app/app.log

Example file:

Tue Mar 9 login-app running
Tue Mar 9 login-app running
6️⃣ Sidecar Reads Logs

The sidecar runs:

tail -f /var/log/app/app.log

So it continuously reads new lines.

Result

If you run:

kubectl logs login-app-sidecar -c log-sidecar

You will see:

Tue Mar 9 login-app running
Tue Mar 9 login-app running
Tue Mar 9 login-app running

The sidecar is streaming the logs.

Verify Shared Storage

Check file from application container:

kubectl exec -it login-app-sidecar -c login-app -- ls /var/log/app

Output:

app.log

1️⃣ Ambassador Pattern
Idea

The Ambassador container acts like a proxy between your application and an external service.

Your application does not talk directly to the external service.
Instead it talks to the ambassador sidecar via localhost.

Architecture:

Application Container
        │
        │ localhost
        ▼
Ambassador Sidecar
        │
        │ network
        ▼
External Service (DB / API / Cache)
Why This Is Useful

The application code stays simple:

connect to localhost:port

The ambassador container handles:

TLS

retries

authentication

connection routing

protocol translation

This is very common in:

Service Mesh (Envoy sidecar)

Database proxies

API gateways

Real Example

Application needs to connect to a remote PostgreSQL database.

Instead of:

App → remote-db.company.com:5432

We do:

App → localhost:5432
        │
        ▼
Ambassador sidecar
        │
        ▼
remote-db.company.com:5432

The ambassador forwards traffic.

Example YAML (Ambassador Pattern)
apiVersion: v1
kind: Pod
metadata:
  name: ambassador-example
spec:
  containers:

  - name: app
    image: busybox
    command: ["sh","-c"]
    args:
      - |
        while true; do
          echo "App connecting to DB via localhost:5432"
          sleep 10
        done

  - name: db-ambassador
    image: alpine/socat
    command:
      - "socat"
      - "TCP-LISTEN:5432,fork"
      - "TCP:remote-db.company.com:5432"

What happens:

App → localhost:5432
      │
      ▼
Ambassador (socat proxy)
      │
      ▼
Remote database
2️⃣ Adapter Pattern
Idea

The Adapter container converts application output into another format.

It adapts the data to something external systems expect.

Architecture:

Application Container
        │
writes data
        ▼
Shared Volume
        │
        ▼
Adapter Sidecar
        │
converts format
        ▼
Monitoring / Logging / Metrics System
Why This Is Useful

Sometimes applications produce data in formats that external systems cannot understand.

Example:

Application logs:

User login successful

Monitoring system expects:

{
  "event": "login",
  "status": "success"
}

Adapter sidecar converts formats.

Real Production Examples

Adapters are commonly used for:

Use Case	Example
Metrics conversion	custom metrics → Prometheus format
Log transformation	text logs → JSON
Monitoring	app metrics → Prometheus exporter
Legacy apps	old format → modern API
Example YAML (Adapter Pattern)

Here we simulate:

app writing logs

adapter converting logs

apiVersion: v1
kind: Pod
metadata:
  name: adapter-example
spec:

  volumes:
    - name: shared-data
      emptyDir: {}

  containers:

  - name: app
    image: busybox
    volumeMounts:
      - name: shared-data
        mountPath: /data
    command: ["sh","-c"]
    args:
      - |
        while true; do
          echo "user_login_success" >> /data/log.txt
          sleep 5
        done

  - name: adapter
    image: busybox
    volumeMounts:
      - name: shared-data
        mountPath: /data
    command: ["sh","-c"]
    args:
      - |
        tail -f /data/log.txt | while read line; do
          echo "{\"event\":\"$line\"}"
        done
Output of Adapter

Adapter prints:

{"event":"user_login_success"}
{"event":"user_login_success"}

Converted format.
