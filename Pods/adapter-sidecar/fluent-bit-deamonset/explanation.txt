Great 👍 This is an important modern Kubernetes logging concept. Earlier many tutorials used sidecar logging, but in real production clusters it is rarely used now. Instead, node-level logging using DaemonSets is preferred.

Let’s understand why Kubernetes moved away from sidecar logging.

1. Sidecar Logging (Old Approach)
Pod Structure
Pod
├── Application Container
│      writes logs → /var/log/app/app.log
│
└── Sidecar Container
       tail -f /var/log/app/app.log
       send logs → logging system

Flow:

Application
   ↓
Log file
   ↓
Sidecar container
   ↓
stdout or log system
2. Problems with Sidecar Logging
1️⃣ Too Many Containers

Every pod needs an extra container.

Example:

Pods	Containers
100 pods	200 containers
1000 pods	2000 containers

This increases:

CPU usage

Memory usage

Scheduling overhead

2️⃣ Resource Waste

The sidecar container runs continuously even when logs are idle.

Example:

Pod
 ├─ app container
 └─ log collector container

The log collector may consume:

50MB memory
some CPU

Multiply this by hundreds of pods.

3️⃣ Hard to Maintain

If you need to update the logging agent:

Example:

fluentd:v1 → fluentd:v2

You must restart every pod.

This causes:

deployment changes

rolling restarts

possible downtime

4️⃣ Application Coupling

The pod spec becomes tightly coupled with logging.

Example pod spec becomes complex:

containers:
- name: app
- name: log-sidecar

If you change logging architecture, all pod specs must change.

3. Modern Kubernetes Logging (Recommended)

Instead of sidecars, Kubernetes recommends:

Node-Level Logging

Use a DaemonSet log collector.

4. What is a DaemonSet?

A DaemonSet runs one pod on every node.

Example cluster:

Node1
Node2
Node3

DaemonSet ensures:

Node1 → log collector
Node2 → log collector
Node3 → log collector
5. Node-Level Logging Architecture

Applications log to:

stdout / stderr

Container runtime stores logs in:

/var/log/pods/
/var/log/containers/

DaemonSet collector reads those files.

Architecture
Application Container
        │
        │ stdout/stderr
        ▼
container runtime (containerd)
        │
        ▼
/var/log/pods/.../0.log
        │
        ▼
DaemonSet Log Collector
(FluentBit / Fluentd / Promtail)
        │
        ▼
Central Log System
(Elasticsearch / Loki / Splunk)

1️⃣ Much Less Resource Usage

This matches the official Kubernetes logging architecture.

Kubernetes documentation recommends:

Application → stdout/stderr

NOT:

Application → log file → sidecar

legacy enterprise applications

The DaemonSet logging system solves a completely different problem: centralized log collection and long-term storage.

Let's break it down clearly.

1. When App Logs to stdout/stderr

As we discussed, the flow is:

Application
   ↓
stdout / stderr
   ↓
container runtime (containerd)
   ↓
/var/log/pods/.../0.log
   ↓
kubelet
   ↓
kubectl logs

So yes — kubectl logs works perfectly here.

But there are several big limitations.

2. Problem 1 — Logs Exist Only on One Node

Logs are stored locally on the node.

Example cluster:

Node1
 ├─ Pod A
 └─ Pod B

Node2
 ├─ Pod C
 └─ Pod D

Logs are physically stored like this:

Node1:
/var/log/containers/podA.log
/var/log/containers/podB.log

Node2:
/var/log/containers/podC.log
/var/log/containers/podD.log

So logs are distributed across nodes.

If you want to search logs across the cluster:

error OR exception

You cannot easily do that with kubectl logs.

3. Problem 2 — Logs Disappear When Pods Die

Imagine this situation.

Pod crashes
Pod deleted
New pod created

What happens?

The log file:

/var/log/pods/<old-pod>

gets removed eventually.

So you lose logs.

Example:

kubectl logs old-pod

will fail because the pod no longer exists.

In production, losing logs is very dangerous.

4. Problem 3 — Hard to Search Logs

Suppose you want to find:

all login failures in last 24 hours

With kubectl logs you would need:

kubectl logs pod1
kubectl logs pod2
kubectl logs pod3
kubectl logs pod4

This is impossible at large scale.

Real systems may have:

1000+ pods
5. Problem 4 — No Log Retention

Node log files are rotated and deleted.

Example node storage cleanup:

old logs removed

So after some time logs disappear.

Companies usually need logs stored for:

7 days
30 days
90 days
1 year

kubectl logs cannot provide this.

6. Problem 5 — No Visualization

With only kubectl logs you cannot easily:

filter logs

search logs

create dashboards

create alerts

For example:

show login errors per minute

This requires a log analytics system.

7. What the DaemonSet Actually Does

The DaemonSet collects logs from nodes and sends them to a central system.

Example DaemonSet:

FluentBit
Promtail
Vector
Fluentd

These agents run one per node.

They read:

/var/log/containers/*.log

and send logs to a central logging system.

8. Full Production Logging Pipeline
Application
     │
     │ stdout/stderr
     ▼
container runtime
     │
     ▼
node log files
/var/log/containers/
     │
     ▼
DaemonSet log collector
(FluentBit / Promtail)
     │
     ▼
Central logging system
(Elasticsearch / Loki / Splunk)
     │
     ▼
UI dashboard
(Kibana / Grafana)

Now you can:

search logs

filter logs

store logs long-term

analyze logs

create alerts

9. Real Example (Grafana Loki)

Instead of running:

kubectl logs pod1
kubectl logs pod2
kubectl logs pod3

You can run one query:

{app="login-service"} |= "error"

and see logs from all pods instantly.

10. What Happens Without a DaemonSet

If you don't have a log collector:

You can only rely on:

kubectl logs

Problems you will face:

1️⃣ Logs disappear when pods restart
2️⃣ Logs are scattered across nodes
3️⃣ Impossible to search cluster-wide logs
4️⃣ No long-term storage
5️⃣ No analytics or dashboards

This becomes a major operational problem.

11. When Sidecar Logging Is Still Needed

You are also correct here.

If the app logs like this:

/var/log/app/app.log

Then node logging cannot see it.

So you must:

1️⃣ modify the app to log to stdout
OR
2️⃣ use a sidecar that tails the file.

But best practice is to modify the app to log to stdout.

12. Final Summary

Your logic is correct, but the missing piece is:

Tool	Purpose
kubectl logs	debugging individual pods
Node log files	temporary storage
DaemonSet logging	centralized log aggregation

So the DaemonSet solves the problem of cluster-wide logging and long-term storage, not log capture.

✅ One sentence answer

The DaemonSet log collector gathers logs from all nodes and sends them to a centralized logging system so logs are searchable, persistent, and aggregated across the entire cluster.

2️⃣ Step 1 — Deploy Elasticsearch

apiVersion: apps/v1

metadata:
  name: elasticsearch

4️⃣ Step 3 — Fluent Bit Config

Create configmap.

fluentbit-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: fluentbit-config
  namespace: kube-system
data:

  fluent-bit.conf: |
    [SERVICE]
        Flush        1
        Log_Level    info

    [INPUT]
        Name tail
        Path /var/log/containers/*.log
        Parser docker
        Tag kube.*

    [OUTPUT]
        Name es
        Match *
        Host elasticsearch.default.svc.cluster.local
        Port 9200
        Index kube-logs

Apply:

kubectl apply -f fluentbit-config.yaml
5️⃣ Step 4 — Deploy Fluent Bit DaemonSet
fluentbit-daemonset.yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentbit
  namespace: kube-system
spec:
  selector:
    matchLabels:
      app: fluentbit
  template:
    metadata:
      labels:
        app: fluentbit
    spec:
      containers:
      - name: fluentbit
        image: fluent/fluent-bit:2.2
        volumeMounts:

        - name: varlog
          mountPath: /var/log

        - name: config
          mountPath: /fluent-bit/etc/

      volumes:

      - name: varlog
        hostPath:
          path: /var/log

      - name: config
        configMap:
          name: fluentbit-config

Apply:

kubectl apply -f fluentbit-daemonset.yaml
